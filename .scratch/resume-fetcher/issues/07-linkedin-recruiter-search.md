# 07: LinkedIn Recruiter real search

**What to build:** A real `linkedinclient` implementation of `PlatformClient.Search` that drives the browser (via the session from ticket 06) to run the confirmed filters as a native LinkedIn Recruiter search and return structured Profile data. `fetch` now returns real candidates from both platforms, exercising the dedup/merge logic from ticket 01 against genuinely overlapping real-world data for the first time.

**Blocked by:** 01, 06

**Status:** ready-for-human

- [x] `linkedinclient.Search(filters)` translates the confirmed filters into LinkedIn Recruiter's native search UI and returns structured Profile data for the results
- [x] The raw result pool from this search is capped (e.g. top 50), matching the pipeline's existing cap from ticket 01
- [x] If a CAPTCHA, 2FA prompt, or apparent rate-limit is hit mid-search, the visible browser pauses and waits for the operator to resolve it, then the search continues automatically
- [ ] Running `fetch --jd <file>` end-to-end now merges real candidates from both Naukri (ticket 04) and LinkedIn, with exact and fuzzy dedup behaving correctly against real data
- [ ] `linkedinclient`'s browser-automation internals are not unit-tested (per the spec's seam); this ticket is verified manually against a real LinkedIn Recruiter account

## Implementation notes

- `linkedinclient.Client.Search` follows ticket 04's `naukriclient.Search` shape exactly: it shares its session-reuse-vs-manual-login decision with `Login` via the `ensureSession()` helper ticket 06 already added, then delegates to a new `browser.Search(state, filters) ([]domain.Profile, error)` method - keeping `Client.Search`'s session/delegation logic unit-tested against a fake in `linkedinclient_internal_test.go` (`TestSearch_ReusesValidSessionAndDelegatesToBrowser`, `TestSearch_NoPersistedSession_FallsBackToManualLoginThenSearches`, `TestSearch_PropagatesBrowserError`, `TestSearch_ManualLoginFailure_IsSurfacedWithoutSearching`), same seam as `naukriclient`.
- The real automation (`rod.go`) navigates to `recruiterSearchURL`, checks the session is still on `recruiterHost` (`requireLoggedIn`, mirroring `naukriclient`'s login-redirect check), drives a native filter form (skills/experience/location/notice period) via go-rod element selectors, clicks the search button, and scrapes result cards into `domain.Profile`. It pauses the visible browser via `waitForChallengeResolution` both before filling the form and after submitting the search, polling the page's rendered text for CAPTCHA/2FA/rate-limit markers (extended with a couple of LinkedIn-flavored phrases, e.g. "security verification") until the operator resolves it or `challengeTimeout` (5 min) elapses - identical mechanism to `naukriclient`'s. `maxSearchResults` (50) defensively bounds how many cards are scraped, matching `pipeline.DefaultConfig`'s `RawPoolCapPerPlatform`, ahead of the pipeline's own cap.
- `profileFromCard` reuses the same `unmatched-N` fallback `ExternalID` scheme as `naukriclient` when the profile-link selector doesn't match a card, so two profiles that both fail to resolve a link can't collide onto the same `Candidate` and silently overwrite each other's data.
- `fetch`'s `selectPlatforms` now wires `linkedinclient.New(session.New(sessionDir), out)` for LinkedIn (reusing `login linkedin`'s session store) instead of the ticket-01 fake, matching how ticket 04 wired the real `naukriclient` in for Naukri. Both platforms now route through real browser automation, so `internal/cli/fetch_test.go`'s prior `--source linkedin` end-to-end tests (which relied on LinkedIn still being fake) no longer have a fake source to exercise; they were replaced with a comment explaining the orchestration logic itself stays covered by `internal/pipeline`'s tests against fake `PlatformClient`s (including real overlapping-data merge/dedup coverage), output writing by `internal/output`'s tests, and this package's own wiring/parsing decisions by `TestParseSources`/`TestSelectPlatforms` in `fetch_internal_test.go`. Only argument-validation tests that fail before any `PlatformClient` is touched (`TestRunFetch_RequiresJDFlag`, `TestRunFetch_RejectsInvalidSource`) remain in `fetch_test.go`.
- **Every CSS selector, the search URL, and the challenge-detection text markers in `rod.go` are unverified against a real LinkedIn Recruiter account** - no browser/network access in this sandbox, same caveat as tickets 03/04/06's `rod.go`. Confirm and adjust them against the real DOM/copy before relying on this in production. Likewise, the fourth checklist item above (real cross-platform dedup against genuinely overlapping Naukri/LinkedIn data) can only be confirmed by actually running `fetch --jd <file> --source both` against real accounts; that and the general automation caveat are this ticket's remaining manual-verification items.
